# BNTS 3D Print Studio

A student file uploader and private teacher console for Banyule Nillumbik Tech School. The design uses the BNTS colours, background and pixel style from [Circuit Pathways](https://github.com/jackallen28/BNTS_Circuit_Pathways), with the supplied BNTS SVG.

**Recommended hosting for 50 MB files: Render (Node).** See [the Render deployment guide](DEPLOY-RENDER.md). Render has a free web-service plan; it sleeps when idle and is subject to usage limits. Files are stored in Google Drive. This option requires one-time Google OAuth client setup and approval by the school account. Students do not sign in.

The Apps Script version remains available for smaller files, with a 10 MB limit set by this app. It avoids manually configuring Google client credentials. Its browser-to-script transfer encodes files as base64, so it is not the recommended deployment for 50 MB uploads.

## Google Apps Script setup

A prepared download can be generated with `npm run package:apps-script`. It contains the built site and these instructions. To build from source, use Node 22 or newer:

```sh
npm ci
npm run build:apps-script
```

1. Sign into the Google account that will own the app. Use a school account that can create and delete files in the printing folder.
2. Create a project at [script.google.com](https://script.google.com/home/start). Name it **BNTS 3D Print Studio**.
3. Replace `Code.gs` with this repository's `apps-script/Code.gs`. Add a script file named **Catalog** and paste `apps-script/Catalog.gs`. Add an HTML file named **Index** and paste `apps-script/Index.html`. The last two files are generated by the build command, and are also in the prepared download.
4. In **Project Settings**, turn on **Show appsscript.json manifest file**. Replace that file with `apps-script/appsscript.json`. Under **Services**, check that **Drive v3** is listed; add it with **+** if needed. The manifest declares the required Google permissions. If you use a separate Google Cloud project, also enable the Google Drive API in that project.
5. In **Project Settings → Script Properties**, add `TEACHER_PASSWORD` with a unique password of at least 12 characters. Keep it for staff only. Do not put it in the HTML or share it with students. The app creates its session signing secret automatically.
6. Choose **Deploy → New deployment → Web app**. Set **Execute as: Me** and **Who has access: Anyone**. Approve Google's permissions using the deploying school account. Your school's Google Workspace policy must allow anonymous web apps; an administrator may need to enable this.
7. Open the deployment's `/exec` URL with **`?page=teacher`** added. Sign in with the teacher password. Keep this staff link private. The password protects the console; hiding its address alone does not protect files.
8. Under **Setup & supplies**, paste the Google Drive folder link, add schools and staff, optionally add classes, select available colours and enable any extra file types. Click **Save setup**. This also creates an hourly cleanup trigger.
9. Share the ordinary `/exec` URL with students. Test one submission, open it in the teacher console, download it and confirm it appears in Drive.

Keep the Drive folder **Restricted**, shared only with the relevant staff. It does not need to be public for students to use this app. A folder link is an address, not an upload credential: the deploying Google account supplies the permission through Google's own authorisation. If the account did not create the folder, give that account permission to add and permanently delete its files. For a Workspace Shared Drive, use a role with deletion rights, such as Content manager.

When updating the site, rebuild, copy the updated files, then use **Deploy → Manage deployments → Edit → New version**. Keep the same script project and deployment to retain settings, sessions and cleanup triggers.

## What students can do

1. Drag in a file or choose one from their computer.
2. View supported models in 3D, rotate and zoom, review model warnings, and select Bambu PLA colours. Unsupported formats display **“Preview not supported for this file type.”** and still upload normally.
3. Confirm their file, add their first name, school, BNTS staff member, optional class, print preferences, notes and optional design link.
4. Review the request and submit. A receipt confirms the file was stored. Retries of the same request do not create duplicate submissions.

STL, OBJ, STEP (`.step` / `.stp`) and 3MF are always accepted. Staff can also enable PLY, OFF, IGES, BREP, Fusion 360, Blender, ZIP and G-code files.

| Format | 3D preview | Notes |
| --- | --- | --- |
| STL | Yes | Assumes millimetres and Z-up. |
| OBJ | Yes | Mesh geometry and vertex colours; separate MTL files/textures are not loaded. Assumes millimetres and Z-up. |
| 3MF | Yes | Core meshes, assemblies, transforms, units, base materials, colour groups and common Bambu object/extruder colours. |
| PLY (optional) | Yes | Mesh geometry and up to 32 colours. Assumes millimetres and Z-up. |
| STEP and other enabled types | No | Originals are stored unchanged. No model checks are claimed for these formats. |

Slicer-specific 3MF painted facets and textures cannot always be rendered accurately. The UI explains this when it detects those features. All original information remains in the uploaded file. Colours chosen in this app are **preferences recorded for staff**, not modifications to the CAD file.

Model checks identify disconnected parts, possible floating components, open/non-manifold edges, degenerate triangles, large or tiny dimensions and likely overhangs. Floating components can be highlighted in the viewer. Checks are advisory: they do not replace a slicer, detect every thin wall, repair meshes or guarantee printability. Detailed topology checks are skipped above 200,000 triangles with an explicit notice. Closed overlapping shells, internal features and some slicer extensions require staff review.

## Teacher console and Drive organisation

Staff can add/remove schools, staff and school-specific classes; choose stocked Bambu PLA Basic colours; allow custom colour requests; and enable additional file types. Existing submissions keep the names and options recorded at submission time.

Browse **School → Class**, or **School → Date** for files with no class. Search, filter by colour/status, and sort by file size, colour, student name or date. Open a file for its larger preview, notes, preferences, original download and Queued/Printing/Printed status. Staff can permanently delete a submission.

Drive folders follow:

```text
Shared printing folder/
  .BNTS Print Studio settings.json
  School/
    YYYY-MM-DD/
      School_Colour_Date_FirstName_Staff_PrintPreferences_Note_Reference.stl
      ...preview.png
      ...details.json
      Class name/
        School_Colour_Date_FirstName_Staff_Class_PrintPreferences_Note_Reference.3mf
        ...preview.png
        ...details.json
```

Dates use **Australia/Melbourne**. No class folder or “no class” text is added when a student does not select a class. File names start with school, colour and date, followed by the student's first name, staff member, optional class, preferences, a shortened note and a unique reference. Long values are shortened for usable file names. Complete notes, links, original name, colour mappings and preferences are kept in the details JSON and the teacher console.

Do not manually rename/move/delete the app's details JSON, settings file or preview files. The console uses these to show files and clean up submissions. Manually copied or exported files are outside the app's retention controls.

## Automatic deletion

Each model, thumbnail and details file is tagged with a 14-day expiry. Expired submissions immediately stop appearing in the console or download API. An **hourly Apps Script trigger** permanently deletes expired artifacts, including incomplete uploads, and removes app-created empty folders. Printed files follow the same retention rule. Settings and unrelated Drive files are preserved.

Deletion runs at the first successful scheduled check after expiry, normally within an hour; Google's scheduling, quotas or outages can delay it. A manual **Clean up now** button and last-success status are available in teacher setup. Check **Apps Script → Triggers / Executions** for failures. The deploying account must remain active and authorised. Do not remove its cleanup trigger. This is automatic retention, not a guaranteed deletion at the exact second of day 14.

## Limits and privacy

- Apps Script uploads are limited to **10 MB per file** to keep browser-to-script transfers practical. The Node/Render host accepts **50 MB** (52,428,800 bytes). This is enforced on both the upload API and the student page. Temporary upload files are removed after each request; completed files are stored in Drive. The UI shows the limit for the current host.
- All students using the Apps Script deployment share Google's execution/Drive quotas. The app caps successful submissions at 120 per hour to reduce anonymous abuse. For large schools or larger files, consider the Node deployment below.
- No student account, surname or email is collected. First name, school and staff selection are required. Staff should avoid requesting sensitive information in notes.
- Teacher sessions last 8 hours. The Apps Script version uses signed tokens, a CSRF check, login throttling and session revocation on logout or password change. Browser session storage is used where available; passwords and Google access tokens are never returned to students.
- Drive's own sharing controls still apply. Do not make the storage folder public. The app does not change its sharing permissions.
- Extra file types are stored as originals. They are not executed or automatically sent to a printer. Staff must check downloaded files before printing. Pre-sliced G-code must match the intended printer.

## Local development

```sh
npm ci
cp .env.example .env
# Fill TEACHER_PASSWORD (12+ characters) and SESSION_SECRET (32+ random characters).
# Keep STORAGE_MODE=local for an explicit local demo with sample school/staff choices.
npm run build
npm start
```

For hot reload, run `npm run dev` and `npm run dev:client` in separate terminals. The Vite client proxies `/api` to port 3000. The local teacher route is `/teacher`. Local demo files go into ignored `.local-data/`; the banner clearly identifies local storage. Production rejects local storage to prevent data loss on ephemeral hosts.

```sh
npm test                  # Domain, geometry, API, retention and Apps Script service tests
npm run build             # Type check and production client build
npm run build:apps-script  # Single-file HTML and Apps Script catalogue
npm run test:e2e           # Real browser student/teacher flows (system Chromium by default)
```

Set `CHROMIUM_PATH` if Chromium is elsewhere. Google service tests use a local Apps Script/Drive adapter, not a live Google account. A live Google deployment still needs the end-to-end smoke test in step 9 above.

## Render and other hosting options

The same frontend also has an Express/Node backend. It is suitable for Render, Cloud Run, Railway or another Node/container host. A Dockerfile and Render blueprint are included. **This option needs a server-side Google OAuth connection; a folder link alone is not enough.** Apps Script avoids manually supplying those credentials, but its current upload limit remains 10 MB. For the requested 50 MB maximum, use the Node/Render version.

For Node production: use `NODE_ENV=production`, `STORAGE_MODE=drive`, `TEACHER_PASSWORD`, `SESSION_SECRET`, `PUBLIC_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `CLEANUP_SECRET`. Enable the Drive API, create a Web OAuth client with redirect URI `PUBLIC_URL/api/admin/google/callback`, connect Google from `/teacher`, and store the returned refresh token securely as `GOOGLE_REFRESH_TOKEN` in host environment settings. Google OAuth apps in Testing may issue refresh tokens that expire after 7 days; use an appropriately configured Workspace/internal or production app for a long-running host. Do not commit secrets.

Use `npm ci && npm run build` for the build and `npm start` for startup. Node storage and settings live in Drive; no paid persistent Render disk is needed. A free Render instance can sleep, so also set the repository variable `ENABLE_NODE_CLEANUP=true` and configure the included hourly GitHub Actions cleanup workflow with repository secrets `PRINT_STUDIO_URL` (the deployed HTTPS origin) and `PRINT_CLEANUP_SECRET` (matching `CLEANUP_SECRET`). It calls `POST /api/maintenance/cleanup` with a bearer token. The app also cleans on startup and hourly while running. GitHub schedules are best effort and can be disabled for inactive repositories; monitor execution and cleanup status. Apps Script's own hourly trigger does not need this workflow.

Plain static HTML alone cannot securely write to a private Google Drive folder or enforce automatic deletion. Dropbox File Requests can accept anonymous uploads, but would not provide this integrated console and retention without an authorised backend.
